在多多买菜一线，最制约效率的是两类工作：选品依赖经验判断，复盘招商依赖重复性的数据分析。AI 解决实际工作问题，需要结果能落地、目标用户能上手。以此为标准，把这两个环节做成一个选品提效项目，从设计、数据、评估三个角度分别展开。

判断一个 AI 产品，我更看重两点：能否交付业务结果，能否让目标用户真正用起来。

行业判断：Agent 不站在用户对面，而是用户的「分身」——把专家级、个性化的服务，带给每一个普通人。这也是选择 AI PM 方向的原因。

项目：多多买菜选品提效

围绕同一业务场景，从三个角度展开，分别验证三块能力（均为公开场景推演，指标为设计预期）

业务背景：多多买菜是拼多多社区团购业务，采销需在节庆/换季窗口前完成选品、招商、复盘。在此业务线从事运营约 1 年。

核心问题：一线两大痛点——选品依赖经验判断，复盘招商依赖手动操作。

解决方案：设计面向采销的选品提效工具，覆盖诊断、选品、招商、复盘四个环节，从设计、数据、评估三个角度展开。

角度一｜产品设计与落地（0→1 概念设计）

证明能力① · 产品设计与落地

这是什么 ▸ 面向多多买菜采销的选品 + 招商 AI 提效工具

解决什么问题 ▸ 节庆换季选品依赖经验、手动排期 8h/周期、招商逐一联系回复率低

关键动作 ▸ 完成需求洞察 → PRD → 信息架构 → 技术选型，确立"AI 生成 + 采销拍板"原则

满足什么需求 ▸ 将采销从重复劳动中解放，选品由经验驱动转向数据驱动

0→1 全链路设计需求→PRD→架构选型方法论
+

面向社区团购采销、依附于内部系统的独立 Web 界面（选品 + 招商），将经验驱动选品转为数据驱动。从 0 到 1 完成产品全流程设计：需求洞察、PRD、信息架构、技术选型；其中"会自己动手查数"的智能核心由 tool-use Agent 实现。

背景与痛点

痛点现状影响
节庆换季无目标采销靠经验选品，无数据支撑招商品质不稳定
排期耗时长手动选品排期 8h/周期效率低，错过最佳招商窗口
招商困难采销逐一联系商家，回复率低招商转化率低，缺品严重

设计目标：选品排期从 8h 压缩至 3h 内，提升招商效率与采销采纳率。

目标用户与场景

  • 用户：社区团购采销（非技术岗，重效率、轻操作）
  • 核心场景：节庆/换季前的选品决策、商家招商、售后复盘

产品决策（PM 思考）

  • 不做全自动替代，采用"AI 生成 + 采销拍板"：采销保留对清单的增删和最终决策权，降低采纳门槛。
  • 用"45 天节庆提醒"把被动响应变主动，抢招商窗口。
  • 招商动作加"72h 冷却 + 15 天 3 次上限"护栏，避免骚扰商家、保护关系。

关键设计细节

本工具按节庆周期分三段，由同一个 Agent 贯穿：节前自动推品（见下方界面示意）→ 节中实时监控 → 节后及时复盘（见其后工作流拆解）。设计原则：以 Agent 为核心，重决策、轻操作——Agent 出初稿，采销做终稿。

节前 · 自动推品 · 信息架构（树状图，节选自设计稿）：从"选区助手 → 筛选 → 出池 → 剔除 → 招商"的完整路径。

智能核心（tool-use Agent）：节日招商流（45 天提醒 → AI 生成招品清单 → 一键招商 → 商家响应 → 冷却策略 → 确认/替换）；节中监控（盯销量与 ROI，识别 ROI 双负即"让利还少卖"→ 提醒调盘）；节后复盘自动化（定时触发 → 拉数据 + 拉去年同期 → 算指标、识别押对/押错品、打标签 → 结论存储 → 日报/周报/月报推送）。这一层由 tool-use Agent 实现，是工具背后"会自己动手查数"的能力。

节中 · 实时监控（销量 + ROI）

开卖期间的监控口径与处置动作。异常才打扰，无异常不推送。

监控项口径判定处置动作
销量销售件数日环比 / 对比预期异常波动（爆量或断崖）补货 / 上调售价控量
ROIGMV 变化率 / 收益率变化差值双负：GMV 变化率 与 收益率变化 同时为负调盘（调整售价） / 换品
让利有效（正向）收益率下降但 GMV 明显增长让利换来销量维持现价，不打扰

关键设计：双负即"让利还少卖"——让出去的利润没换回销量，是最该被及时干预的信号；同时保留"让利有效"的正向结论，避免把降价换成销量的品误判为问题品而误伤。

真实产品评测：扣子（Coze）

  • 业务价值：降低 Agent 搭建门槛，把开发从代码中释放。
  • 用户价值：任务驱动型产品（有活开、没活关），低门槛是留存关键；个人日均使用 1h+，门槛低带来高于同类的留存。
  • AI 质量：准确率较高、幻觉率低；响应速度 10s–1min 偏慢。
  • 可持续：无 novelty effect 风险；费用较高是门槛；AI 迭代快有替代风险。
  • 关键洞察：扣子是"任务驱动型"而非"日常陪伴型"，这决定了其使用模式与留存逻辑。
